# P24 工程问题审查接入计划

状态 planned。P23 完成远端冻结后推进本阶段；此计划不代表新增审查能力或评测已完成。

目标：利用 P20 多项目结果、P21 配置影响、P22 ARXML 和 P23 独立 ECU 证据，回答有来源的工程问题。沿用现有确定性审查、引用复验和拒答内核；先固定问题与判定，再判断是否存在需要可选模型解释的缺口。

## 实现顺序与验收

1. 固定至少 30 个不同工程问题，覆盖六类：配置变更影响、跨层引用/布局、ARXML 支持边界、项目门控与验收、外部构建/寻址/诊断、来源缺失/迁移/篡改。每项绑定输入版本、期望结论、必须引用的证据、禁止推断的内容；不能把同一问题换词凑数。
2. 接入 P21/P22/P23 报告消费者，复用来源核验。区分规则结论、检索命中和自然语言解释，不让模型覆盖实际工程状态。
3. 开发集之外单独保留未参与规则调优的负例集合；记录形成/冻结顺序和 hash，不能将开发中已经使用的失败样例改名冒充独立负例。
4. 分别计量检索、确定性判定、引用正确性、严重度保真和拒答；若增加可选模型，单独报告其增益和无证据断言，不混入确定性成功率。
5. 提供可重放命令、报告与真实失败用例；本实现独立七 job CI 验收，上传评测证据，再更新首页、路线和下一任务。

首批应回答的问题包括：某配置变化影响哪些验收项、静态失败为何阻止 ECU 启动、CF01 超时有哪些尚不能区分的原因、项目通信通过能否证明 OpenBSW 使用该 DBC、两次不同构建/诊断条件为什么不可直接比较。它们是需求候选，尚未作为冻结数据集或通过率发布。

商业工具许可与物理 ECU 不作为本阶段已有事实；只引用已验收范围。平台实现与使用者自己的源码定位、协议解释和复跑学习分别记录。
